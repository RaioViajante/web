# Multilingual architecture

The contract for English and Brazilian Portuguese across the four sites. It
turns the tracking issue
([#22](https://github.com/RaioViajante/web/issues/22)) into rules that the
implementation must follow and the reasons for them. The architecture is
accepted and implemented incrementally: only slices that have landed are
implemented, and the remaining "must" statements are the target contract.
Statements about current behavior describe the repository as it is at the time
of writing.

## Status and scope

- **Status:** decision record, accepted and normative. Implementation child
  issues follow it.
- **Languages:** English (the existing language and default) and Brazilian
  Portuguese. Another locale must be addable later without changing the model,
  but no third locale is planned.
- **Applications:** all four (Root, Dump, Docs, Lab). Each one is part of the
  final target. Rollout may be phased; no application is permanently
  English-only.
- **Authoring:** every localized text is written by hand. There is no machine
  translation and no generated content.
- **Coverage:** partial. A post, document, experiment or page may exist in only
  one language, indefinitely. Parity is never required.

## Goals

- Keep every existing English public URL working and meaning what it means now.
- Give Brazilian Portuguese explicit public URLs on the same hosts.
- Make the rendered locale a deterministic function of the URL.
- Keep the SEO guarantees in [seo.md](seo.md) for every localized page.
- Keep translation identity independent of URLs, filenames, titles and dates.
- Keep the existing RSS subscribers, comment threads and search contracts.
- Add no browser storage, no client framework and no i18n dependency by default.

## Non-goals

- Machine translation or automatic content generation.
- Mandatory EN/PT parity for any item.
- Moving current URLs under `/en`.
- Automatic redirects by `Accept-Language`, browser language or IP.
- Persisting the language in cookies, `localStorage` or any other browser state.
- Flags as the only language affordance.
- A CMS, a translation-management service or a generic translation platform.
- Speculative support for many locales.
- The SP clock, the SOUND restyle and any utility-row redesign unrelated to
  `LANG`. They belong to a separate shared-UI task.
- Implementing the system in this document.

## Terminology

These words have one meaning in this document and in the code that implements
it.

| Term                     | Meaning                                                                                                                                                                                                                                                                                          |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| locale                   | One entry of the locale registry: a language plus, where it matters, a region. The internal identifiers are `en` and `pt-BR`.                                                                                                                                                                    |
| language                 | The ISO 639-1 part of a locale (`en`, `pt`).                                                                                                                                                                                                                                                     |
| region                   | The ISO 3166-1 part of a locale where one is declared (`BR`). `en` declares no region in its identifier.                                                                                                                                                                                         |
| work                     | The underlying thing that can exist in several languages: a post, a documentation page, an experiment, or a static page.                                                                                                                                                                         |
| localized version        | One work in one locale, with its own URL, text and lifecycle dates.                                                                                                                                                                                                                              |
| original                 | The localized version in which a content work was first written. Every content work has exactly one; route-registry pages do not track one.                                                                                                                                                      |
| translation              | Any localized version of a work that is not its original.                                                                                                                                                                                                                                        |
| counterpart              | Another published localized version of the same work. Two versions are counterparts only through a shared `contentId` or route key, never by matching text.                                                                                                                                      |
| `contentId`              | The stable, locale-neutral identifier of a work. It never changes once published and is not derived again from a slug, path, filename, title or date.                                                                                                                                            |
| route key                | The `contentId` equivalent for ordinary application pages (`about`, `search`), declared in an app's route registry.                                                                                                                                                                              |
| slug                     | The locale-specific URL segment of one localized version.                                                                                                                                                                                                                                        |
| app locale participation | Whether an app's public contract in a locale is live in production and verified. Declared once per app and locale in shared configuration, and turned on only after that verification (see [Publish before advertise](#publish-before-advertise)). It drives every cross-host use of the locale. |

## Locale registry

One shared, typed registry defines the locales and every protocol-specific
spelling of them. It is normative:

| Concept                      | English | Brazilian Portuguese |
| ---------------------------- | ------- | -------------------- |
| Internal locale              | `en`    | `pt-BR`              |
| Language                     | `en`    | `pt`                 |
| Region                       | none    | `BR`                 |
| URL prefix                   | none    | `/pt`                |
| HTML `lang`                  | `en`    | `pt-BR`              |
| `hreflang`                   | `en`    | `pt-BR`              |
| Open Graph locale            | `en_US` | `pt_BR`              |
| Structured-data `inLanguage` | `en`    | `pt-BR`              |
| RSS `<language>`             | `en`    | `pt-BR`              |
| `Intl` formatting locale     | `en-US` | `pt-BR`              |
| Accessible language name     | English | Português (Brasil)   |
| Compact label                | `EN`    | `PT`                 |

Rules:

- English is the default locale: unprefixed, and the `x-default` target of
  every cluster that has an English member.
- Brazilian Portuguese is explicitly regional (`pt-BR`, not `pt`) because its
  vocabulary and formatting target Brazil.
- `en_US` and `en-US` are the values the sites already use (Dump's `og:locale`
  and Dump's date formatting, the only date formatting in the apps). They do
  not change.
- Protocol mappings and user-facing locale behavior come from the registry.
  Every app, `seo/` and `packages/design` read `lang`, `hreflang`,
  `og:locale`, `inLanguage`, RSS `<language>`, `Intl` locale, URL prefix and
  language names from it.
- The supported locale values themselves may appear elsewhere where that is
  necessary: framework-required route directories (such as a `pt` folder),
  exhaustive `switch` statements and other control flow over the supported
  locales, content declarations (`locale: pt-BR`), type unions derived from the
  supported locales, and tests and fixtures. Such code must not redefine a
  protocol mapping, invent an unsupported spelling, or keep its own copy of a
  URL, Open Graph, `hreflang` or other mapping. The goal is one semantic source
  of truth, not a ban on the string `pt-BR`.

Why one registry: the same locale has six spellings (`pt-BR`, `pt_BR`, `pt`,
`/pt`, `Português (Brasil)`, `PT`). When each app spells them itself, one of
them drifts. `lang`, `hreflang`, `og:locale`, `inLanguage` and RSS
`<language>` then disagree for the same page, and nothing catches it. Today
`lang="en"` is written separately in each layout, `inLanguage: "en"` is in
`seo/structured-data.ts`, Dump has its own `site.locale`, and only Dump emits
`og:locale` at all. The registry replaces all of them.

The registry lives in `site/` (see [Ownership boundaries](#ownership-boundaries)).

## URL model

- English keeps the current URLs exactly. There is no `/en` and no migration.
- Brazilian Portuguese uses the `/pt` prefix on the same host:
  `raioviajante.com/pt`, `dump.raioviajante.com/pt/...`,
  `docs.raioviajante.com/pt/...`, `lab.raioviajante.com/pt/...`. There are no
  separate hosts.
- Each app keeps its current trailing-slash convention, under `/pt` too. Root
  and Dump (Next.js) have no trailing slash. Docs and Lab (Astro,
  `trailingSlash: "always"`) end every page path with `/`. Every URL the
  system emits (canonical, `hreflang`, sitemap, feed, search entry, language
  control) uses the host's own form. Changing a host's trailing-slash policy is
  out of scope.
- Structural segments (`posts`, `tags`, `archive`, `experiments`, `search`)
  stay as in English under `/pt`. Content slugs may differ
  per locale. Static application pages mirror their English path under `/pt`
  by default. An app may give one a localized path, but only in its route
  registry.
- The exact first host-level path segment `pt` is reserved for locale routing,
  on all four hosts. `/pt` and `/pt/...` are reserved. A path is not prohibited
  merely because it contains `pt`: `/posts/pt-debugging`, `/http/` or
  `/experiments/pt-example/` are fine, because nested segments and slugs never
  collide with the locale prefix. A first segment such as `/ptx` is also
  unaffected. The rule matters most in Docs, whose catch-all `[...slug]` route
  would otherwise turn a top-level content folder named `pt` into a Portuguese
  URL.
- A missing translation is a missing route: the Portuguese URL does not exist
  and answers 404. It is never a Portuguese page shell around untranslated
  English main content, indexable or not.
- After publication, a localized version's slug changes only by exception.
  When it does, the old URL answers a permanent redirect to the new one in the
  same locale. Redirects never cross locales.
- Locale detection never changes what an existing URL serves.

| App  | English                     | Portuguese                   |
| ---- | --------------------------- | ---------------------------- |
| root | `/`, `/about`               | `/pt`, `/pt/about`           |
| dump | `/posts/<slug>`             | `/pt/posts/<slug-pt>`        |
| docs | `/projects/sweep/cli/`      | `/pt/projects/<path-pt>/`    |
| lab  | `/experiments/boot-sector/` | `/pt/experiments/<slug-pt>/` |

## Locale authority

The URL is the only authority for the rendered locale. A path under `/pt` is
Portuguese, and every other path is English.

Never used:

- automatic `Accept-Language` redirects;
- IP- or geography-based redirects;
- browser-language redirects or content swaps;
- a locale cookie;
- `localStorage`, `sessionStorage` or any other browser storage for locale.

A language change is ordinary navigation to another public URL, by the visitor.
Shared behavior reads the locale from the rendered document (`<html lang>`),
not from the browser.

Why: the sites are static or server-rendered and cached. A URL that renders
different languages for different visitors cannot be cached, canonicalized or
shared reliably. Storage would also add to the browser storage inventory
([privacy-storage.md](privacy-storage.md)), which today holds one preference
cookie. Browser language may later be used only as a non-authoritative hint,
such as a dismissible suggestion, and only if a separate decision approves it.
It must never change routing, canonical metadata or rendered content.

## Route and counterpart model

Each app declares which of its URLs exist and how they relate. Two
complementary records cover all four apps:

- **Route registry** for ordinary application pages (Root's `/about`, every
  app's home, `search`, `archive`, `privacy`, `terms`). Each entry has a route
  key and, per locale where the page exists, its path. Static pages do not
  need content frontmatter for this.
- **Content records** for works that are authored as content (Dump posts, Docs
  pages, Lab experiments). Each localized version carries the identity fields
  in [Content identity model](#content-identity-model).

From these, every page can answer deterministically: which locales does this
page exist in, and what is the URL of each counterpart? `seo/` builds
canonical and `hreflang` tags from that answer, and `LANG` builds its links
from it.

The model must support:

| Case                      | Behavior                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| Translated route          | Both paths are declared under one key. Each page links to the other through `hreflang` and `LANG`.       |
| One-language-only route   | Only one path is declared. No alternate is emitted, and `LANG` follows its no-counterpart state.         |
| Localized slug difference | Paths are independent per locale. Identity comes from the key, not the path.                             |
| Counterpart added         | Declaring the new path adds it. The original URL does not change.                                        |
| Counterpart removed       | Removing the path removes the alternates on the remaining version. That version keeps working unchanged. |

Every declared path must be a real built page. Every built localized page must
be declared. A test checks both directions.

## Content identity model

Every localizable work has these concepts. The exact storage (frontmatter,
data module, collection schema) is app-owned:

| Field            | Scope             | Meaning                                                            |
| ---------------- | ----------------- | ------------------------------------------------------------------ |
| `contentId`      | work              | Stable locale-neutral identity. Unique within the app.             |
| `locale`         | localized version | A registry locale.                                                 |
| `originalLocale` | work              | The locale of the original. The same on every version of the work. |
| `slug`           | localized version | Locale-specific URL segment.                                       |
| `publishedAt`    | localized version | See [Date semantics](#date-semantics).                             |
| `updatedAt?`     | localized version | See [Date semantics](#date-semantics).                             |

The identity fields are required for every content work. Dates are required
only where the app already has them: Docs and Lab have no publication date
today, and none is invented for them.

Requirements:

- Identity never depends on title, slug, pathname, filename or date, and is
  never inferred by matching any of them across locales.
- `(contentId, locale)` is unique: at most one version per locale.
- A work has exactly one original. Its `locale` equals `originalLocale`.
- Portuguese-original and English-original works are equally valid.
- A work needs no counterpart in any other locale.
- Slugs belong to the localized version and do not affect identity.
- Adding a translation never changes the original's URL. Removing one never
  breaks the original.
- A build fails on a duplicate `(contentId, locale)`, a work without exactly
  one original, or a version whose `originalLocale` disagrees with the
  others'.

### Withdrawing the original

`originalLocale` is immutable historical provenance. It is never reassigned,
including when the original's public page is withdrawn.

- If the original is withdrawn while translations stay public, the app keeps
  knowledge of the work's original locale in a nonpublic record, such as a
  tombstone or an unpublished version entry. The physical form is app-owned.
  The remaining translations keep their `contentId`, their `originalLocale`
  and their URLs.
- The withdrawn original is no longer a counterpart. Alternates, `LANG` links
  and feed items for it disappear, as for any removed version.
- The "exactly one original" build check counts that nonpublic record. A work
  whose public versions are all translations is valid only when the record
  exists.
- If an app cannot retain that provenance safely, it withdraws all localized
  versions of the work together. It never promotes a translation to original.

### Existing content gains identity without changing URLs

The migration assigns each existing work a `contentId` equal to its current
identifier, then stores it explicitly so it never depends on the filename
again:

- Dump: the current slug (today, the filename). For example,
  `building-orbit` keeps `/posts/building-orbit` and gets `contentId`
  `building-orbit`.
- Docs: the current content-collection entry id, the path under
  `src/content/docs` (for example `projects/sweep/cli`).
- Lab: the existing experiment `id` (`001`, `002`, `003`), which is already a
  stable publication number separate from `slug`.

Every existing version gets `locale: en` and `originalLocale: en`. No English
URL, slug or filename changes. After the migration, renaming a file or slug
must not change `contentId`. A build check enforces that `contentId` is
declared and not derived.

## Date semantics

Dates belong to the localized version being rendered. Each localized version
has the simplest sufficient lifecycle:

```text
publishedAt
updatedAt?
```

| Version     | `publishedAt`                                          | `updatedAt`                                          |
| ----------- | ------------------------------------------------------ | ---------------------------------------------------- |
| Original    | When that original-language version first went public. | Latest explicit material update of that version.     |
| Translation | When that translation first went public.               | Latest explicit material update of that translation. |

- The relationship to the original comes from `contentId` and
  `originalLocale`. If the UI shows the original's publication date on a
  translation, for example "originally published in English on …", it
  resolves it from the original's record and does not copy it.
- `updatedAt` is optional and only ever explicit. It is never derived from
  build time, deployment time, Git timestamps, or another locale's changes.
  Publishing a translation does not update the original.
- Dump's `publishedAt` is the authoritative first-publication field of each
  English post, and `updatedAt` is optional, set only for a material update of
  that localized version. No Git, author, filesystem, build or deployment
  timestamp supplies either. Docs' `lastUpdated` is that localized page's
  `updatedAt`, and Docs pages still have no publication date. Lab's `created` and `revision`
  describe the experiment itself, the same for every locale. They are not
  document lifecycle dates and feed no `lastmod` or `dateModified`.
- Implications, matching [seo.md](seo.md):
  - `datePublished` is that version's `publishedAt`.
  - `dateModified` and sitemap `lastmod` appear only together, both from that
    version's `updatedAt`, and never equal to `publishedAt`.
  - RSS `pubDate` is that version's `publishedAt`.
  - Dates render in UTC with the registry's `Intl` formatting locale.

## SEO

Every localized page meets the existing contract in [seo.md](seo.md): one
title, description, canonical on the production host, `og:*` and `twitter:*`
tags with a real social card, icons, manifest and theme color. The rules below
add language.

### Canonical

- Each indexable localized page canonicalizes to itself: absolute, production
  host, the host's trailing-slash form, no query.
- A complete Portuguese translation never canonicalizes to its English
  counterpart, or the reverse.
- Search pages keep one bare canonical per locale (`/search`, `/pt/search`;
  `/search/` and `/pt/search/` on Astro hosts).

### `hreflang`

- A page with at least one real published counterpart emits a complete
  cluster: itself and every counterpart, plus `x-default` only when that
  cluster has a valid explicit default under the [`x-default`](#x-default)
  rule below.
- Values come from the registry (`en`, `pt-BR`). URLs are fully qualified
  production URLs in the host's form.
- Clusters are reciprocal and identical on every member.
- A page with no counterpart emits no `hreflang` at all, not even a
  self-reference. It never invents an alternate.
- Removing a translation removes it from the remaining cluster in the same
  build.
- Search pages emit the cluster for their two locales when both exist. The
  existing `noindex, follow` stays.

### `x-default`

- In the current EN/PT model, every real cluster has an English member, and
  `x-default` points to it. That is the existing unprefixed default, also when
  the original is Portuguese.
- With no cluster there is no `x-default`.
- Future locales: if a real cluster contains an English member, `x-default`
  points to that member. If a cluster has no English member, no English URL is
  invented: `x-default` is omitted, unless an explicit valid default page has
  been defined for that cluster.

### HTML `lang`

- On every normal page (indexable, search, any localized route), `<html lang>`
  is the registry value for the route's locale: `en` or `pt-BR`.
- On a 404 page, `<html lang>` matches the language of the copy actually
  rendered (see [404 behavior](#404-behavior)).
- `lang` always describes the element's own text. Inline text in the other
  language carries its own `lang`, for example the other language's name in
  `LANG` or a language name inside a cross-language link label. The language
  of a link's destination is stated by `hreflang`, not by `lang` (see
  [Cross-language related links](#cross-language-related-links)).
- In the Next.js apps (Root and Dump), the server-rendered `<html lang>` must
  match the URL locale on initial loads (`en` for English URLs, `pt-BR` under
  `/pt`) and stay correct after client navigation. Multiple locale root
  layouts through route groups are one valid implementation. The app's
  implementation slice chooses and verifies the mechanism. English URLs must
  not change.

### Open Graph locale and alternates

- `og:locale` is emitted on every page from the registry (`en_US`, `pt_BR`).
  Today only Dump emits it. Root, Docs and Lab gain it.
- `og:locale:alternate` lists each real counterpart's locale only. It is not
  emitted when there is no counterpart.
- `og:title`, `og:description`, `og:image:alt` and `twitter:*` text are in the
  page's locale. Each localized page has its own social card, using the
  existing renderer and `/og/<path>.png` scheme with the localized title.

### Structured data

`inLanguage` depends on the node type, not merely on the page having a locale:

| Node                              | Language rule                                                                                                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WebPage`                         | `inLanguage` is the rendered page's locale, where a `WebPage` node is emitted (today as `mainEntityOfPage` on posts).                                                            |
| `BlogPosting`                     | `inLanguage` is the rendered article's locale. URL, text and dates are that version's.                                                                                           |
| `TechArticle`                     | `inLanguage` is the rendered document's locale. URL, text and dates are that version's.                                                                                          |
| `WebSite` (`/#website`)           | One stable `@id` per host. Where language coverage is stated, `inLanguage` is the set of locales the host has actually shipped, the same on every page that emits the full node. |
| `Blog` (Dump, `/#blog`)           | Same rule as `WebSite`.                                                                                                                                                          |
| `BreadcrumbList`                  | No `inLanguage`. Item names are localized, and item URLs are real pages in the page's locale.                                                                                    |
| `Person` and other identity nodes | Never inherit the page locale. The `Person` identity in `seo/structured-data.ts` does not change.                                                                                |

- Host-level entities keep one `@id` per logical entity. A given `@id` never
  carries contradictory language declarations across pages: either every full
  node states the same shipped set, or the full node stays on the English home
  page and Portuguese pages reference it by `@id`, as every page already
  references the shared `Person`.
- Translation relationships may be stated with `workTranslation` and
  `translationOfWork` between real counterparts only. They are optional
  enrichment and never replace `contentId`.

### Indexing and `noindex`

- Every real localized page is indexable, unless it falls under an existing
  `noindex` class (search, 404), in both locales.
- No page is `noindex`ed or hidden to work around duplicate content. The
  architecture never creates duplicates: there are no fallback shells and no
  English main content on any `/pt` page. The one English page that can be
  served for a `/pt` URL is the `noindex` 404 fallback on Docs and Lab (see
  [404 behavior](#404-behavior)), and it answers for URLs that do not exist.

### 404 behavior

Every 404, in either language, is a real HTTP 404, `noindex`, with no
canonical, no `hreflang` and no sitemap entry. Its `<html lang>` matches the
copy actually rendered. English error copy is never presented as Portuguese
merely because the failed URL starts with `/pt`.

A Portuguese 404 is required wherever the framework and deployment can serve
one deterministically for the `/pt` tree. An English fallback is accepted only
where they cannot without disproportionate infrastructure change, and only if
the visible copy is genuinely English, `lang="en"`, the status is 404, the page
is `noindex`, and it has no canonical, no `hreflang` and no sitemap entry.

| App  | Accepted behavior for a missing URL under `/pt`           | Basis                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| root | Portuguese 404, `lang="pt-BR"`. Required.                 | Next.js renders segment-level `not-found` UI when `notFound()` is invoked. The Portuguese route tree must deterministically handle unmatched paths and missing resources. The missing-resource decision must occur before the response body starts streaming. Before participation is enabled, production verification must prove that representative `/pt` misses return HTTP 404 with Portuguese copy and `lang="pt-BR"`. Unmatched URLs outside `/pt` keep today's English 404.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| dump | Portuguese 404, `lang="pt-BR"`. Required.                 | Dump's request proxy derives the locale from the URL and checks post and tag paths against a build-generated form of the authoritative published inventory. It decodes a tag segment once, normalizes Unicode to NFC, encodes the authoritative identity once, and rejects malformed encodings, residual percent escapes and encoded separators. English tag lookup remains case-insensitive for historical compatibility; Portuguese tag lookup uses the declared canonical case exactly. A dynamic miss is rewritten to a guaranteed-unmatched path in the same locale before rendering begins. Next.js normalizes repeated separators and one trailing slash with its established 308 before the proxy; a missing normalized destination then receives this localized 404. The proxy also handles repeated separators safely if a deployment runtime passes them through. This preserves the requested URL for direct misses and produces the localized root not-found document with status 404; `notFound()` is not the primary dynamic-miss mechanism because Next.js 16 otherwise emits its error shell without a reliable document language. |
| docs | English fallback 404 (`404.html`), `lang="en"`. Accepted. | Static Astro output with no adapter. Vercel serves the single root `404.html` for every missing path. A `/pt/404.html` page would never be selected. A rewrite would answer 200, and path-scoped status routing would mean replacing the `vercel.json` headers configuration or adding an adapter, which is disproportionate for an error page.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| lab  | English fallback 404 (`404.html`), `lang="en"`. Accepted. | Same as Docs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

Edge and application responsibilities for Dump's malformed targets differ. The
Vercel edge rejects request targets containing invalid UTF-8 percent-encoding
with HTTP 400 before the application runs, so no localized document can be
served for them; this is platform request validation and is not bypassed. The
application handles everything that reaches it: encoded separators and valid
missing routes under `/pt` return the localized HTTP 404. Issue #47's 404
criterion therefore applies to well-formed targets; the edge 400 for
malformed UTF-8 is recorded as an explicitly accepted platform behavior,
pending the owner's confirmation on the issue.

Root and Dump keep declaring `robots: { index: false }` on their not-found
metadata in both trees, as described in [seo.md](seo.md). If Docs or Lab later
gain an adapter or routing layer that can return a real 404 with a Portuguese
page under `/pt`, the Portuguese 404 becomes required there too.

## Sitemap

- One `/sitemap.xml` per host, as today, through `seo/`'s serializer.
- Every real indexable localized URL is its own entry, in both locales.
- Locale alternates are emitted in the HTML `<head>` only. Sitemap
  `xhtml:link` alternates are not added unless implementation shows a
  concrete need. Two copies of the same cluster would need two consistency
  checks for no gain.
- `lastmod` appears only from that localized version's explicit `updatedAt`.
- Each sitemap URL equals that page's canonical, as `pnpm seo:verify` already
  enforces. Search and 404 pages stay out in both locales.

## Robots

Locale creates no robots policy. One `/robots.txt` per host stays as is
(`Allow: /`, one Sitemap line). Nothing under `/pt` is blocked. Blocking
`/pt/search` would hide its `noindex`, as with `/search` today.

## Search

| Locale     | Page                                | Index                   |
| ---------- | ----------------------------------- | ----------------------- |
| English    | `/search` (Astro: `/search/`)       | `/search-index.json`    |
| Portuguese | `/pt/search` (Astro: `/pt/search/`) | `/pt/search-index.json` |

- `/search-index.json` stays the English index. Its URL and current entry
  shape are a public contract that other hosts' search pages read.
- Each entry gains `locale`, and `contentId` where the entry is a work.
  Entries in one index all share that index's locale. Once the field is
  required (see the migration order below), a reader rejects an index whose
  entries carry a different locale, as it already rejects one whose `site` does
  not match.
- The four hosts deploy independently, so the English schema change follows
  [Publish before advertise](#publish-before-advertise):
  1. Every host's `/search-index.json` adds `locale: "en"` to its entries.
     Existing readers keep working: today's reader checks only the array shape
     and `site`, and ignores additive fields.
  2. All four production English indexes are deployed and verified.
  3. Only then may readers start requiring `locale`. A newer reader never
     rejects an older, still-valid production index just because deployments
     happened in a different order. Until that point, an English entry without
     `locale` is read as `en`.
- Search covers the current locale by default. The "everywhere" scope is
  federated within the current locale: Portuguese reads each host's
  `/pt/search-index.json`.
- Languages are never mixed silently. A cross-language search may be added
  only as an explicit visitor action. Results from mixed searches then show
  their language in words.
- Federation must tolerate partial coverage:
  - An app that has not shipped the locale, according to app locale
    participation, is not fetched. The UI says in words that it has no
    Portuguese results yet.
  - A participating app whose index cannot be fetched is reported as
    unreachable, as today, and the rest still searches.
  - A published locale whose normative searchable inventory has no entries
    returns an empty index (`[]`), not a 404. Participation alone neither
    requires nor permits an empty index: if published searchable destinations
    exist, an empty index is a validation failure.
- Matching uses `toLocaleLowerCase` with the registry locale. Dates use the
  registry's `Intl` formatting locale. Whether accents are folded is decided
  once in the shared engine, for both locales.
- Following the language control on a search page carries `q` to the other
  locale's search page, and only when that search experience is actually
  available: the app participates in both the current and the target locale.
  No other query parameter,
  fragment or page state is carried. Queries are never stored.
- Search UI copy (prompts, result counts, empty and unavailable messages) comes
  from the shared catalogs.
- The suggestions offered when nothing matches are terms that the locale's
  published index answers. `SearchPage` accepts them as optional `suggestions`;
  an app that publishes a locale passes terms taken from that locale's real
  index, and a test fails if one finds nothing.

### Cross-language related links

This applies to every related-content block in every app (Dump related posts,
Dump-to-Lab links, Docs and Lab cross-references):

- Related content is same-locale by default. When no same-locale target exists,
  nothing from the other language is substituted automatically.
- A link to content in the other language is allowed when it is intentionally
  chosen as editorially relevant. It names the target language in words, for
  example "Failure-first architecture — English", carries `hreflang` for the
  linked resource, and points directly to the real public page.
- `lang` describes the visible link text, not the destination. It goes on the
  whole link only when the whole label is in that language. Otherwise it goes
  only on the foreign-language fragment. A Portuguese label for an English page
  does not get `lang="en"` on the whole link. The exact markup is an
  implementation detail. One correct shape on a Portuguese page, where the
  English title is the only foreign-language fragment and "em inglês" inherits
  the page's `pt-BR`:

  ```html
  <a href="https://dump.raioviajante.com/posts/…" hreflang="en">
    <span lang="en">Failure-first architecture</span> — em inglês
  </a>
  ```

- It is never presented as same-locale content and never creates or implies a
  localized counterpart. The principle is the same as for legal links:
  cross-language navigation is allowed when explicit, never silent.
- Exact wording is editorial and comes from catalogs or app copy.

### GUID compatibility

Today every item's GUID is its permalink,
`<guid isPermaLink="true">https://dump.raioviajante.com/posts/<slug></guid>`.
Feed readers use the GUID as the item's identity. A changed GUID shows an old
post as new.

- **Existing items:** every English post published before the migration keeps
  its current GUID string verbatim, forever. The migration records that set
  from the live `/rss.xml` before any change. A test fails if a recorded GUID
  changes or disappears while its post is published. `isPermaLink="true"`
  stays as long as the GUID equals the item's `<link>`. If such a post's slug
  is later changed by exception, the GUID text stays and `isPermaLink` becomes
  `false`.
- **Every other localized version** (new English posts, all Portuguese
  versions) gets a non-permalink GUID derived only from `(contentId, locale)`:
  `tag:dump.raioviajante.com,2026:post/<contentId>/<locale>`, with
  `isPermaLink="false"`. The host is the production constant from `site/`
  (never the build's origin) and `2026` is fixed forever, so the string cannot
  change with slug, title, date, order or deployment. A translation therefore
  never shares a GUID with its original.
- **Migration boundary:** the GUID rule is in `apps/dump/lib/rss-identity.ts`.
  `LEGACY_ENGLISH_CONTENT_IDS` is the closed set of 12 English works that were
  in the live feed on 2026-10-19. Those keep `<production origin>/posts/<contentId>`
  (equal to the old slug-based permalink, because their contentId was their
  slug) in their English version only. The set never grows; every other item,
  including new English posts, uses the tag form. The captured production feed
  and its extracted identities are
  `apps/dump/tests/fixtures/production-rss-2026-10-19.xml` and
  `legacy-rss-identity.json`; `tests/legacy-rss-identity.test.ts` fails if a
  recorded GUID, link, `pubDate` or `isPermaLink` changes or disappears while
  its post is published. Retiring a legacy post is an editorial act that edits
  that fixture in the same change.
- **isPermaLink** is `true` exactly when the GUID equals the item's `<link>`:
  true for legacy items on the production origin, false for tag GUIDs and for a
  legacy item whose slug was changed (the GUID text stays).
- Unless a post was added or removed, the English feed has the same items
  before and after the migration, with byte-identical GUIDs, links and
  `pubDate` values.

## Giscus

Decision: the translations of one Dump work share one discussion.

- Each work has a locale-independent `commentKey`. Every localized version of
  the work uses the same discussion through it.
- Giscus switches from `data-mapping="pathname"` to `data-mapping="specific"`
  with `data-term` set to the `commentKey`. `data-strict="1"` stays.
- `commentKey` is `posts/<contentId>`. Existing posts' `contentId` equals their
  slug, so their key equals the exact term giscus derives from today's
  pathname (`/posts/<slug>` without the leading slash). Their existing
  discussions keep matching without any remapping.
- The giscus UI language (`data-lang`) follows the rendered locale, using
  giscus's code for Brazilian Portuguese. giscus supports a single Portuguese
  interface, `pt` (no `pt-BR` exists in its `i18n.js` list), so Portuguese
  articles use `data-lang="pt"`.

### Migration and audit

The current mapping is `pathname`, strict (`data-strict="1"`), in the
`Comments` category
([apps/dump/docs/comments.md](../apps/dump/docs/comments.md)). At the time of
writing the repository has one discussion: #14,
`posts/maybe-this-can-be-something-someday`, with one comment. Its strict
marker matches the SHA-1 of the proposed `commentKey` for that post. Before the
mapping changes:

1. **Snapshot.** Capture a migration snapshot of every discussion in the
   `Comments` category. Each entry records at least the discussion number, the
   node ID (if available), the URL, the category ID, the title, the strict
   marker, the comment count, and the post it belongs to.
2. **Preview verification.** On a preview deployment with the `specific`
   mapping, prove for each snapshot entry that the computed `commentKey`
   resolves the exact same discussion (same node ID or number, not merely the
   same title) and shows the same existing comments. A matching title is not
   enough. Verification is read-only: nothing is posted, reacted to or
   otherwise changed in any production discussion.
3. **Switch.** Production keeps `pathname` until step 2 succeeds for every
   entry. If any discussion would not match, implementation stops and reports
   it. It does not create, rename, merge or edit discussions to compensate.

Existing discussions must not be abandoned, duplicated or split between old and
new identities.

## Language selector

`LANG` is the shared language control. This section defines its behavior. Its
visual treatment in the shared utility row is a separate shared-UI task.

- It is navigation, so it uses links to real URLs, not a stateful toggle. It
  works without JavaScript, which matters on the Astro hosts, where shared
  React renders without hydration.
- The only visible state is `LANG EN` or `LANG PT`, naming the current locale.
  A direct link carries `hreflang` for its destination and an accessible name
  that states both the current language and the switch action. The disclosure
  uses the same compact face and names the target in its accessible action.
  Every accessible name of the control (link, disclosure summary and status)
  begins with the exact visible text, followed by a dash and the explanation in
  the page's language, so speech input and assistive technology that match the
  visible label reach it (WCAG 2.5.3, Label in Name): `LANG PT — Idioma:
  Português (Brasil). Mudar para inglês.` Flags are not used.
- Keyboard operable, visible focus, 44px targets, and an accessible name that
  states the current language and the action.
- It stores nothing.

Participation is evaluated before counterpart availability. If either the
current route's locale or the offered target locale is not participating for
this app, `LANG` remains a noninteractive status of the current language until
both locales participate. This applies
[Publish before advertise](#publish-before-advertise) to the control: a
Portuguese route that is already deployed but not yet verified, and reached
directly, advertises no cross-locale navigation. English, the default, always
participates.

Every state is fixed. Implementation does not choose between alternatives:

| Situation                                  | Behavior                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current or target locale not participating | `LANG` is a noninteractive status of the current language, with no link and no disclosure: `LANG EN` on an English page before Portuguese activation, `LANG PT` on a directly visited pre-activation Portuguese page. It is never removed, so every app shows `LANG` consistently. This row takes precedence over all others.                                                 |
| Both participate, exact counterpart exists | The target language choice links directly to the counterpart (`/about` ↔ `/pt/about`, post ↔ its translation).                                                                                                                                                                                                                                                                |
| Both participate, no counterpart           | The control opens a disclosure under the target language name. It states that this page is not available in that language, and always provides a separate, labeled link to the target locale's home of the same app. That link is never styled or labeled as a translation of the current page. This includes Portuguese-only content, symmetrically toward the English home. |
| Search page, both participate              | Links to the target locale's search page, carrying `q` only.                                                                                                                                                                                                                                                                                                                  |

Example disclosure for the third row (final copy is editorial and localized):

```text
Português (Brasil)
This page is not available in Portuguese.
Go to Portuguese home →
```

The links come from the page's route or content record and from app locale
participation at render time, so a page never links to a counterpart that is
not built or to a locale that is not live. Once all four apps participate,
every app offers the active EN/PT choice.

## Publish before advertise

The four hosts deploy independently, so one host cannot know that another's
new deployment is live. Invariant: no shared configuration, and no host,
claims that an independently deployed host supports a locale until that host's
public contract in the locale is live and verified in production.

For each app's Portuguese activation:

1. Build and deploy the app's Portuguese routes and required localized public
   endpoints (`/pt` pages, `/pt/search-index.json`, and for Dump `/pt/rss.xml`)
   while its participation stays off in shared configuration. Same-host
   `hreflang` and sitemap entries ship with the routes, because they are built
   in the same deployment, and Portuguese pages link within their own tree.
   `LANG` on that app stays noninteractive, and no other host advertises the
   locale.
2. Verify the actual production URLs and endpoints: status, content type,
   `lang`, canonical, sitemap entries, and index or feed contents.
3. Only then turn on that app's Portuguese participation in shared
   configuration, in a separate change. Participation lives in `site/`, which
   every app's Ignored Build Step watches, so that change rebuilds all four
   hosts.
4. Only after that change is deployed do other hosts and shared UI use the
   locale for that app.

This gates every cross-host use of a locale:

- `LANG` destinations and its participation state;
- federated search, which fetches only participating apps' Portuguese indexes;
- feed integration (Root Portuguese reads `/pt/rss.xml` only once Dump
  participates);
- cross-site navigation, footers and related links into another host's `/pt`
  tree;
- any other cross-host locale participation.

Schema changes to an existing public contract follow the same order: producers
first, verified on all hosts, then readers may require the change. See the
English search migration in [Search](#search). A reader never rejects a
still-valid older producer.

Turning participation off reverses the order. Shared configuration stops
advertising first, and the routes are withdrawn only afterwards.

## Shared UI catalogs

- `packages/design` owns the text of shared UI only: Shell navigation labels,
  footer, the sound control's states and accessible names, `LANG`, search
  prompts and messages, pager labels, 404 shared copy.
- Each app owns its editorial copy: page text, taglines, project and
  experiment descriptions, legal text, `llms.txt` discovery copy (in `seo/`).
- Catalogs are small, typed, explicit objects keyed by registry locale. A
  missing key in any shipped locale fails type checking or a test. There is no
  global untyped translation blob, no runtime fetch of strings, and no fallback
  that silently shows English inside a Portuguese page.
- Shared client behavior, such as the sound toggle's accessible label, gets
  its strings for the document's locale rendered into the page or from the
  catalog selected by `<html lang>`.
- The soft blocks (copy, copied, show all N lines, show less, the file tab list,
  callout labels, footnote names and the names of sideways-scrolling regions)
  are in the catalog's `blocks` section. The markup pipeline renders them for
  the document's locale at build time: the `rehypeSoftBlocks` option `locale`,
  or, without it, the `locale` the document's own frontmatter states (Astro
  content collections), or English. The block behavior also repaints any
  control still in English from the catalog selected by `<html lang>`, so a
  Portuguese page built by a pipeline that stated no locale is still correct,
  and it announces "copied" through a polite status. An author's own callout
  label is never translated.

## Dependency policy

No third-party i18n framework by default. The starting point is:

- the typed locale registry in `site/`;
- small typed UI catalogs in `packages/design`;
- app-owned route registries and content records;
- shared locale-aware helpers in `seo/`.

Why this is enough: two locales, hand-authored text, no plurals beyond what a
catalog function can express, and static or server rendering everywhere.
Next.js App Router has no built-in locale routing for this model. Astro's
optional i18n routing would cover only half the apps and would add a second
model. Explicit route records give both frameworks the same contract. A
framework may be introduced only when an accepted decision shows a requirement
the explicit model cannot reasonably meet.

Locale is always an explicit registry value passed through. There are no
`isEnglish` or `isPortuguese` booleans. Code that branches on locale does so
exhaustively over the supported locales, so that a third locale fails type
checking until it is handled, and never re-derives a protocol mapping (see
[Locale registry](#locale-registry)). No translation-management
infrastructure is built speculatively.

keys, comments, repository documentation, commits, PRs, GitHub issue metadata
and stable internal ids, including `contentId`, route keys and tag identities.

- translated page copy, posts, documents and experiment text;

engineering language, and Portuguese is allowed only for the intentional
public localized artifacts listed above and the tests and fixtures that verify
them. The first foundation slice established that exception before any
Portuguese content lands.

## Phased rollout

Every phase leaves all four sites correct: no link into a locale that is not
shipped, no fake fallback, and no change to English output except added
Portuguese alternates.

1. **Locale contracts and validation.** Registry and participation in `site/`,
   route and content record contracts, reserved `pt` segment, and the
   `AGENTS.md` authoring exception. Every app is declared as not participating
   in Portuguese yet.
2. **Locale-aware SEO foundation.** Canonical, `hreflang`, `x-default`,
   `og:locale`, node-specific `inLanguage`, sitemap, search-path rule, and
   checks in `seo/`, with English output unchanged apart from `og:locale` on
   Root, Docs and Lab. The English search indexes add `locale: "en"`. Readers
   start requiring it only after all four production indexes are verified.
3. **Shared `LANG` and catalogs.** Catalogs, language control, and locale-aware
   search and sound text in `packages/design`. No app participates yet, so
   every app renders the noninteractive `LANG EN` status.
4. **Root.** Portuguese routes and the Portuguese 404, deployed and verified,
   then participation on ([Publish before advertise](#publish-before-advertise)).
   The Dump integration points at `/pt/rss.xml` only once Dump participates.
   Until then Portuguese Root shows its stated empty state.
5. **Dump content model.** `contentId`, locale fields, per-locale slugs, tags,
   series, archive and navigation. Existing identity is captured as described
   above.
6. **Dump routes and search.** Portuguese pages, the per-locale index and the
   Portuguese 404 are published and verified while participation stays off.
7. **Dump RSS and Giscus.** `/pt/rss.xml` and localized autodiscovery follow in
   #48 without changing legacy English GUIDs. Stable discussion identity
   follows in #49 without changing the existing English pathname mapping.
   Production verification comes next, then Dump participation.
8. **Docs.** Identity capture, per-locale navigation, routes and index,
   verified in production, then participation on.
9. **Lab.** Per-locale experiment content, localized key labels and bench
   strings, verified in production, then participation on.
10. **Cross-site verification.** Federation across all four, `LANG` on every
    app, and the full validation list below.

Slice boundaries may move during implementation. The final target, EN and
PT-BR on all four apps, does not.

## Validation strategy

The implementation must add checks for each item, inside the existing
`pnpm validate`, `pnpm seo:verify`, `pnpm security:check`, link and browser
checks where they fit:

| Check                       | Rule                                                                                                                                                                                                                                                                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTML `lang`                 | On normal pages, equals the registry value for the route's locale, in the server-rendered HTML and, on Root and Dump, after client navigation. On 404 pages, equals the language of the rendered copy, per the per-app 404 table. Replaces the current `lang="en"` rule in `seo/metadata-policy.ts`.                          |
| 404 responses               | Real 404 status, `noindex`, no canonical, no `hreflang`, not in the sitemap. Root and Dump serve Portuguese copy with `pt-BR` under `/pt`. Docs and Lab serve the English `404.html` with `lang="en"`.                                                                                                                        |
| Canonical                   | Self, absolute, production host, host trailing-slash form, equal to the sitemap URL.                                                                                                                                                                                                                                          |
| `hreflang`                  | Self plus every declared counterpart, reciprocal, identical across the cluster, absolute URLs that are real sitemap pages; none without a counterpart.                                                                                                                                                                        |
| `x-default`                 | Present exactly when a cluster with an English member exists, pointing to that member. Omitted otherwise, unless an explicit default page was defined.                                                                                                                                                                        |
| Open Graph locale           | `og:locale` from the registry on every page; `og:locale:alternate` only for real counterparts.                                                                                                                                                                                                                                |
| Structured data: content    | `WebPage`, `BlogPosting` and `TechArticle` carry `inLanguage` equal to the rendered locale, with localized URL, text and dates that agree with the page and the feed.                                                                                                                                                         |
| Structured data: identity   | `Person` keeps its single `@id` and carries no page locale. `WebSite` and `Blog` keep one `@id` per host, and any `inLanguage` on them is the shipped-locale set, identical wherever the full node appears.                                                                                                                   |
| Structured data: breadcrumb | `BreadcrumbList` has no `inLanguage`. Item names are in the page's language, and item URLs are real sitemap pages in the page's locale.                                                                                                                                                                                       |
| Sitemap/canonical agreement | Both locales, no search or 404 pages, `lastmod` only from explicit `updatedAt`.                                                                                                                                                                                                                                               |
| Titles and descriptions     | Unique within a locale. Equal values across locales are allowed only between counterparts.                                                                                                                                                                                                                                    |
| No fake localized fallbacks | No `/pt` page whose main content is the English counterpart's, and no undeclared `/pt` page.                                                                                                                                                                                                                                  |
| Route/counterpart integrity | Every declared path is built and every built localized page is declared; `(contentId, locale)` unique; one original per work, public or kept as a nonpublic provenance record; `originalLocale` never changes.                                                                                                                |
| Visible labels              | No raw internal key (Lab `status` and `fidelity`) and no English field label on a Portuguese page. Dates use the page locale.                                                                                                                                                                                                 |
| Cross-language links        | Every link to the other language names that language in words and carries `hreflang` for its destination. `lang` matches the label's own text: on the whole link only when the whole label is in that language, otherwise only on the foreign-language fragment. | Search locale integrity     | Every entry's `locale` matches its index; federation skips non-participating apps and survives unreachable ones.                                                                                                                                                                                                              |

No cross-host link, feed read or fetch targets a non-participating app's `/pt` tree.                                                                                                                         |
| RSS language and GUID       | `<language>` per feed; recorded legacy GUIDs unchanged; new GUIDs from `(contentId, locale)`; each item in its locale's sitemap.                                                                                                                                                                                              |

Otherwise, a direct counterpart link, or the disclosure with the unavailable statement and the separate home link. Search carries `q` only. |
| `LANG` accessibility        | Accessible names, `lang` for each choice label's own text and `hreflang` for each destination, keyboard operation, visible focus, 44px targets, axe clean.                                                                                                                                                                    |
| Keyboard and mobile         | Utility row and language choices at phone width without overflow, in both locales.                                                                                                                                                                                                                                            |

## Migration concerns

These need preservation work, not naïve replacement:

- **Existing English URLs.** Capture every sitemap URL per host before the
  first change and check them after every slice.
- **Dump RSS GUIDs.** Record the live GUID set, then pin it with a test (see
  [GUID compatibility](#guid-compatibility)).
- **Giscus discussions.** Snapshot and read-only preview verification before
  switching from `pathname` to `specific` (see
  [Migration and audit](#migration-and-audit)).
- **English search contracts.** `/search-index.json` URL and entry shape stay
  compatible for the other hosts' readers. New fields are additive, producers
  ship before readers require them, and readers never reject an older
  producer.
- **Cross-host activation.** Every app's Portuguese participation follows
  [Publish before advertise](#publish-before-advertise).
- **Production origins.** No new origin source. Dump's existing two sources
  stay as they are (see [Dump's origin](#dumps-origin)).
- **Current sitemaps and canonicals.** English canonical URLs and sitemap
  entries stay byte-identical. The only additions are Portuguese entries,
  English-page `hreflang` where a counterpart exists, and `og:locale` on
  Root, Docs and Lab.
- **Identifiers derived from filenames.** Dump slugs, Docs entry ids and Dump
  series keyed by slug are captured into explicit `contentId` values before
  any rename.

## Invariants

- Existing English URLs stay valid and keep their content.
- The URL alone determines the rendered locale.
- Switching language never depends on cookies, browser storage, request
  headers or IP.
- A localized URL serves content actually authored for that locale.
- Every indexable page canonicalizes to itself.
- `hreflang` and `og:locale:alternate` never point to a page that does not
  exist.
- Translation identity is independent of slug, path, filename, title and date.
- `(contentId, locale)` identifies at most one localized version, and each work
  has one original, whose `originalLocale` is never reassigned.
- Protocol mappings and user-facing locale behavior come only from the
  registry. There are no locale booleans and no duplicated mappings.
- Publish before advertise: no host or shared configuration advertises a
  locale for another host before that host's contract is live and verified.
- Cross-language links are always explicit and language-labeled, never a
  silent fallback.
- Existing RSS subscribers are not shown old items as new.
- Existing comment discussions are not discarded, duplicated or split.
- Apps never import one another, and `site/` imports nothing.
- No phase links into a locale an app has not shipped.
