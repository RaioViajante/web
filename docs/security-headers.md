# Production security headers — Phase 4

## Recovery and scope

Work started on `chore/production-hardening`, with a clean working tree and
`232a57d chore: update vulnerable dependencies` at HEAD. The only inherited
commit ahead of `main` was that dependency remediation commit. No deployment,
push, dashboard, DNS, external repository, or later hardening phase is included.

The installed frameworks are Next.js 16.3.8 and Astro 7.3.6. The current Docs app
does **not** use Starlight: the earlier design migration removed it. All four
apps use a fixed dark palette, with no theme bootstrap or theme-switch control.
Astro renders shared React statically; there are no hydrated React islands.
Giscus already loads near the viewport; that implementation is unchanged.

## Architecture

`security/headers.ts` contains the common header values and an app-specific CSP
builder. It is ordinary repository infrastructure, not part of the design
package and not a new workspace dependency. Next config and each app's proxy
consume it directly. Astro's build keeps scripts and CSS external using
`vite.build.assetsInlineLimit: 0` and `build.inlineStylesheets: "never"`.

Docs and Lab get literal HTTP headers in `vercel.json`, generated by
`node security/sync-vercel.mjs`. `pnpm security:check` checks for drift and audits
every generated HTML file. Astro preview uses the same values via its supported
`server` callback. No meta-only CSP is used: `frame-ancestors` requires HTTP.
All four Ignored Build Steps watch `../../security` (now 230 characters, with `../../seo` also watched).

The original static build contained one inline module in Lab's index. Astro's
own extraction removes it. Docs already had only external script elements.
Both static apps have external CSS. Shared Shiki emits classes, not inline
styles. Root's existing Next Image `color:transparent` and ten gallery animation
delays, and Lab's existing `display:contents`, are allowed by exact SHA-256 style
attribute hashes. No production directive permits `unsafe-inline` or
`unsafe-eval`; script event-handler attributes are denied.

## Next nonce flow

Each app's `proxy.ts` generates 16 cryptographically random bytes using Node's
`randomBytes`, encoded as base64 (128 bits of entropy). It overwrites incoming
`x-nonce` and CSP headers, forwards both via `NextResponse.next({ request: {
headers } })`, and sets the identical CSP on the response. Next itself extracts
the nonce from the **request CSP** and attaches it to framework scripts, chunks,
and streamed inline scripts. The app does not rewrite Next's HTML.

Root awaits `connection()` in its root layout. Dump reads `headers()` in its
root layout and article page, which also supplies the nonce to its own JSON-LD
script elements. Those request APIs opt HTML into dynamic rendering. The
documented `strict-dynamic` mechanism lets nonced framework scripts load their
dependencies, including the existing programmatically inserted Giscus script.
In CSP3 browsers, `self` and the Giscus script origin are compatibility fallbacks
and are ignored for script loading: trust propagates from nonced scripts. Other
resource types retain their explicit origin allowlists.

The proxy covers HTML routes, errors, RSC/navigation requests, and prefetches.
It deliberately does not skip requests based only on client-supplied prefetch
headers. `/_next/static`, `/_next/image`, and exact known icon, manifest, robots,
sitemap and search-index paths are excluded; Dump also excludes RSS and
`giscus.css`. Social-image paths pass through the proxy because an unknown slug
returns an HTML 404 that also needs a nonce. Valid social images remain static
and cacheable, but incur the proxy step. Static responses outside the proxy
receive the non-nonce policy from Next config. Next's image optimizer retains
its own restrictive image-response CSP.

Development alone allows the documented Next `unsafe-eval` requirement and
development style injection, and omits HTTPS upgrading. Production verification
uses `next start` and `astro preview`, not development servers.

## Rendering and caching

| App  | Before                                                                              | After                                                |
| ---- | ----------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Root | Static HTML; homepage ISR every 60 seconds                                          | All document routes and the app 404 render on demand |
| Dump | Static home, archive, search, legal and tag index; SSG articles and individual tags | All document routes and the app 404 render on demand |
| Docs | Nine static HTML pages, including 404                                               | Same static output                                   |
| Lab  | Eight static HTML pages, including 404                                              | Same static output, index script extracted           |

Next's observed document cache header is now
`private, no-cache, no-store, max-age=0, must-revalidate`. HTML and RSC cannot use
the full-route cache, ISR or shared CDN caching; never cache a document with its
nonce for reuse. Root's explicit RSS **data** fetch cache still revalidates at
60 seconds. Metadata, RSS, search JSON, CSS, fonts and images retain their
existing static generation and caching. No Cache Components/PPR is enabled.

Expected Vercel effects are additional proxy and rendering work per page/RSC
request, more compute usage, and potentially higher latency and cold-start
costs than CDN-served HTML. Dump now also compiles its existing MDX on article
requests; no markdown runtime is shipped to the browser. These are consequences
of the approved nonce/dynamic-rendering architecture. Local builds and HTTP
checks do not measure Vercel billing, regional latency or production cold starts.
No additional server runtime was introduced for Docs or Lab.

| Lab  | `connect-src` | `https://raioviajante.com`, `https://dump.raioviajante.com`, `https://docs.raioviajante.com`     | Everywhere search                                                 |
| Dump | `script-src`  | `https://giscus.app`                                                                             | `client.js`; CSP2 fallback, with nonce trust propagation in CSP3  |

| Dump | `frame-src`   | `https://giscus.app`                                                                             | The comments widget                                               |

There are no other non-self CSP origins. The Giscus iframe performs its own API
and GitHub/avatar requests under its own policy: the parent does not need
`github.com`, `api.github.com` or avatar origins in `connect-src` or `img-src`.
The iframe fetches Dump's existing `giscus.css`; its existing Giscus-specific
CORS response remains unchanged.

Permissions Policy denies unused camera, microphone, geolocation, screen
capture, payment, USB, fullscreen and clipboard-read capabilities. It retains
first-party audio and code-copy access; Root has no code-copy controls, so it
denies clipboard-write too. Dump additionally permits clipboard-write for the
Giscus iframe, matching its actual `allow` attribute. Names were checked against
the [W3C feature registry](https://github.com/w3c/webappsec-permissions-policy/blob/main/features.md).
Browser support differs; Firefox reports Giscus's clipboard-write iframe
permission as unsupported, rather than as a CSP violation.

COOP is `same-origin` everywhere. Giscus's actual
[sign-in link](https://github.com/giscus/giscus/blob/main/components/CommentBox.tsx)
uses `target="_top"`, and its OAuth callback redirects back to the article.
There is no opener-dependent authentication popup requiring a weaker COOP.
The inspected public client was downloaded from
[Giscus](https://giscus.app/client.js); no third-party code is vendored.

## Validation and limits

Run with Node 24.20.0 and pnpm 12.8.1:

```sh
NEXT_PUBLIC_SITE_URL=https://dump.raioviajante.com pnpm -r build
NEXT_PUBLIC_SITE_URL=https://dump.raioviajante.com pnpm validate
node security/verify-http.mjs
git diff --check
```

The HTTP verifier expects production servers on Root 3002, Dump 3001, Docs 4321
and Lab 4322. Start them with the corresponding named filter's `start --port`
or `preview --ignore-lock --host 127.0.0.1 --port` command. `--ignore-lock`
preserves any pre-existing Astro preview. Do not deploy to run these checks.

Local browser testing uses `root.localhost`, `dump.localhost`, `docs.localhost`
and `lab.localhost` at those ports. Unlike bare localhost, these names avoid the
existing search client's development-only cross-port probes, so the exact
production origin allowlist is exercised. No localhost origins are added to
production CSP. Everywhere search still fetches the public sibling indexes.

Astro preview does not attach `server.headers` to its own missing-route fallback.
The HTTP verifier therefore checks the built `404.html` directly for the static
apps. Production `vercel.json` has an all-path rule, including errors; its actual
host behavior remains a post-deployment verification item. Next's real 404s,
including unknown social-image paths, are checked locally.

Giscus's script, stylesheet link, iframe, resizing and unauthenticated comments
UI load under the parent CSP. Firefox blocks the public iframe's access to the
local custom-theme URL under Local Network Access protection. The CSS endpoint
and its CORS header are checked over HTTP; this local browser restriction is
not bypassed. No comment was posted, no GitHub authorization was granted, and
an authenticated round trip was not performed. Production custom-theme loading
must be rechecked after an authorized deployment.

No visual or content changes are intended. Browser smoke checks cover gallery
hydration, sound, navigation, search, article rendering, copy controls and Lab
interactions, including keyboard and mobile checks. These are not an exhaustive
accessibility audit or a cross-browser certification. Theme switching,
Starlight behavior and hydrated Astro React islands are absent from the
checkpoint and are not claimed as tested features.

No securityheaders.com, Mozilla Observatory, deployment or rollout validation
is claimed. Node emits a non-failing module-type inference warning for the
shared TypeScript configuration, as it already does for the design package.
