## Visão geral

O Orbit pretende ser um agendador de jobs distribuído e self-hosted: você define jobs, o Orbit os executa em um horário ou sob demanda, e cada execução é registrada separadamente, de modo que exista um histórico do que rodou, quando e com qual resultado. No desenho pretendido, workers em máquinas diferentes recebem as execuções e reportam os resultados.

:::important
O Orbit ainda não agenda nem executa nada. Hoje o servidor guarda definições de jobs, registra execuções e impõe as regras do ciclo de vida de uma execução. Nenhum código lê uma expressão cron, inicia um comando, aplica um timeout ou repete uma falha.
:::

## Arquitetura

O servidor é uma aplicação Spring Boot 4.1.1 em Java 25, construída com Maven. Usa Spring Web MVC, Spring Data JPA, Bean Validation e Flyway, e conversa com o PostgreSQL. O único arquivo de infraestrutura é um serviço de Docker Compose que sobe o PostgreSQL 17 para desenvolvimento.

O código é organizado por funcionalidade e depois por camada:

```text
dev.raioviajante.orbit
  job/        domain · application · infrastructure · web
  execution/  domain · application · infrastructure · web
```

A camada de domínio contém entidades JPA que protegem as próprias invariantes. A camada de aplicação contém os serviços, a de infraestrutura contém os repositórios do Spring Data, e a web contém os controladores e os records de requisição e resposta. As respostas são records explícitos, então as entidades nunca saem do servidor.

`spring.jpa.hibernate.ddl-auto` está em `validate`: o Hibernate confere o esquema mas nunca o altera, e o Flyway é dono de toda mudança. `spring.jpa.open-in-view` está desligado.

## Modelo de dados

Um job descreve um trabalho. Uma execução é uma rodada de um job. Um job tem várias execuções, e uma execução pertence a exatamente um job.

```sql
CREATE TABLE jobs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    command TEXT NOT NULL,
    cron_expression VARCHAR(100),
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    max_retries INTEGER NOT NULL DEFAULT 0,
    timeout_seconds INTEGER NOT NULL DEFAULT 300,
    -- created_at e updated_at omitidos
    CONSTRAINT jobs_max_retries_check CHECK (max_retries >= 0),
    CONSTRAINT jobs_timeout_seconds_check CHECK (timeout_seconds > 0)
);
```

A tabela `executions` repete `command`, `max_retries` e `timeout_seconds` do job, e acrescenta `status`, `created_at`, `started_at`, `finished_at`, `exit_code` e `error_message`. Uma restrição do banco limita `status` aos cinco valores conhecidos, e um índice cobre `job_id`.

Copiar as três configurações é proposital: uma execução nasce de um instantâneo do job, então editar o job depois não reescreve o que uma execução passada devia rodar. As notas de arquitetura mencionam um número de tentativa para as execuções, mas o esquema ainda não tem essa coluna.

## Ciclo de vida da execução

Uma execução começa como `QUEUED`. O objeto de domínio aceita apenas estas transições e rejeita qualquer outra com uma `IllegalStateException`:

```text
QUEUED  --start-->   RUNNING
RUNNING --succeed--> SUCCEEDED   (registra o código de saída)
RUNNING --fail-->    FAILED      (registra o código de saída e uma mensagem não vazia)
QUEUED | RUNNING --cancel--> CANCELLED
```

`SUCCEEDED`, `FAILED` e `CANCELLED` são terminais: nenhum método sai deles. Um job desabilitado não pode criar execuções, e pedir uma resulta em um conflito. Como nada chama `start`, `succeed` ou `fail` fora dos testes, toda execução criada pela API permanece `QUEUED`.

## Validação

A entrada é conferida duas vezes. Os records de requisição usam Bean Validation: o nome é obrigatório e tem no máximo 120 caracteres, o comando é obrigatório, a expressão cron é opcional mas não pode estar em branco nem passar de 100 caracteres, as retentativas devem ser zero ou mais, e o timeout deve ser maior que zero. As classes de domínio então impõem as mesmas regras de novo, de modo que uma entidade não pode ser construída em estado inválido por nenhum chamador. A expressão cron não é interpretada, então um valor que não seja cron válido é aceito hoje.

## Limitações

- Nada executa comandos. O campo `command` é texto armazenado.
- Não há autenticação nem modelo de permissões, então a API não deve ser exposta além de uma rede confiável.
- As credenciais padrão do datasource ficam em `application.properties` para desenvolvimento local.
- Não há agendamento, reivindicação nem travas, então duas instâncias do servidor ainda não coordenariam nada.
- Não há empacotamento: rodar o Orbit significa compilá-lo com Maven e subir o PostgreSQL pelo arquivo do Compose.
